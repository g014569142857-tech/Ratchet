# Ratchet 项目知识手册

> **棘轮（Ratchet）**：一种只能单向转动的齿轮。
> 用它命名这个项目，是因为它精确描述了我们要做的事——**让大模型的每一次使用，都变成它下一次表现的垫脚石，能力只往上卡一格，绝不滑回去。**

副标题：**让任何大模型越用越懂你的本地自强化引擎**

本手册面向非专业读者。你不需要有机器学习背景，我们从最底层的概念讲起，一路讲到这个项目的完整架构。读完之后，你应该能独立回答"这个项目到底在做什么""为什么这么做""哪些地方有风险"。

## 1. 先搞清楚一件事：大模型是怎么"变强"的

一个训练好的大模型，本质上就是**一大堆数字**（叫"参数"或"权重"）。GPT-4 级别的模型有上万亿个这样的数字。模型回答问题时，就是把这些数字拿来做一堆矩阵乘法，最后算出"下一个字应该是什么"。

关键结论：**模型的能力，只存在于这堆数字里。**

所以"让模型变强"只有两种可能：

| 方式 | 通俗解释 | 是否需要动那堆数字 |
|---|---|---|
| **参数化提升** | 重新雕刻这堆数字（训练/微调） | 需要 |
| **非参数化提升** | 数字不动，但改变"喂给模型的信息"和"如何处理模型的输出" | 不需要 |

这个区分是理解整个项目的钥匙。你最初的设想——"让任何大模型自己强化自己"——在这两条路上有完全不同的可行性和难度。

## 2. 两条完全不同的技术路线

### 路线 A：参数化（真·训练模型）

**做法**：拿到模型的权重文件，用数据去更新这些权重。

**能做到的效果**：能力提升是"内化"的，模型本身变聪明了，不依赖外部提示。

**致命限制**：
- **闭源 API 模型（GPT、Claude、Gemini、千问 API）根本拿不到权重。** 你只能发请求、收文本，无法修改。对这些模型，路线 A **物理上不可行**，不是难度问题，是可能性问题。
- 开源模型（Qwen、Llama、Mistral、DeepSeek 等）可以，但需要 GPU。做 LoRA 微调至少需要 16GB 显存（7B 模型量化后），做完整 RL 训练需要多卡 A100/H100 级别。
- 训练有**灾难性遗忘**风险：为了学会新东西，可能把原有的通用能力弄坏。

### 路线 B：非参数化（不动权重，动"上下文"和"流程"）

**做法**：模型权重完全不动。我们建一套外部系统，在模型**推理前**给它塞入精选的经验，在模型**推理后**评估结果、记录教训、优化下一次的策略。

**能做到的效果**：模型表现得"越来越懂你"。虽然权重没变，但因为每次都能调取到相关的历史经验和已验证有效的策略，实际输出质量持续提升。

**核心优势**：
- **对任何模型都有效**，包括闭源 API。只要能发请求就能用。
- **零 GPU 依赖**，一台笔记本就能跑。
- **完全透明可解释**：所有"学到的东西"都是人类可读的文本记录，你可以直接打开看、手动改、随时删。
- **可回滚**：出问题了删掉某条经验就行，不会把模型搞坏。

**局限**：
- 模型的基础推理能力上限没变。它不会突然学会它本来完全不会的数学。
- 提升来自"更好地调用已有能力"和"避免重复犯错"，而非"获得新能力"。

### Ratchet 的选择：**分层架构，B 为核，A 为可选扩展**

这是经过权衡后的推荐方案，理由：

1. **覆盖面最大化**。你要求"让任何大模型"都能用——只有路线 B 满足这个前提。
2. **可运行性**。你要求 MVP 能真跑起来、能上 GitHub 让别人 `pip install` 就用——路线 B 不需要 GPU，受众是所有人。
3. **不牺牲深度**。我们把路线 A 做成**可选训练后端**：如果你手上是开源模型且有 GPU，Ratchet 积累的经验数据可以直接导出成 DPO/GRPO 训练集，真的去更新权重。这样"自我强化"就有了完整的两层含义。
4. **数据是共享资产**。路线 B 积累的经验库，本身就是路线 A 最需要的训练数据。先做 B，等于顺便为 A 铺好了数据管道。

## 3. 核心概念词典

按理解顺序分组。每个概念都配一句"这跟 Ratchet 有什么关系"。

### 3.1 大模型基础

**Token（词元）**
模型处理文本的最小单位，不是字也不是词，是介于两者之间的碎片。英文大约 1 token ≈ 0.75 个单词，中文大约 1 token ≈ 1～1.5 个汉字。所有的计费和长度限制都按 token 算。
→ *Ratchet 要控制注入经验的 token 量，否则会挤占正文空间、增加成本。*

**上下文窗口（Context Window）**
模型一次能"看到"的 token 总量上限，包括你的输入、历史对话、系统提示和它的输出。常见 8K～200K。超出就会被截断，模型直接"看不见"。
→ *这是 Ratchet 最硬的约束。经验库可能有几万条，但每次只能塞进去几条，所以"检索得准"比"存得多"重要。*

**提示词 / 系统提示（Prompt / System Prompt）**
你发给模型的文本。系统提示是优先级最高的那部分指令，定义模型的角色和行为规范。
→ *Ratchet 的一个核心动作就是**动态改写系统提示**——把学到的经验编进去。*

**温度（Temperature）**
控制输出随机性的参数。0 = 每次都选概率最高的字（稳定但死板），1 以上 = 更随机（有创意但容易胡说）。
→ *Ratchet 在"探索新策略"时会调高温度，在"执行已验证有效策略"时调低。*

**推理（Inference）**
模型生成回答的过程，区别于"训练"。你日常用 ChatGPT 就是在做推理。
→ *Ratchet 的所有非参数化提升，都发生在推理的前后，不碰推理本身。*

### 3.2 参数化训练相关（路线 A 的词汇）

**微调（Fine-tuning）**
在已训练好的模型上，用你自己的数据继续训练，让它适应特定任务或风格。
→ *Ratchet 的可选后端。*

**SFT（Supervised Fine-Tuning，监督微调）**
最基础的微调：给模型看"问题 → 标准答案"的配对，让它模仿。
→ *Ratchet 可以把高分经验导出成 SFT 数据集。*

**LoRA（Low-Rank Adaptation，低秩适配）**
一种省资源的微调技术。**不去改原来那一大堆权重，而是在旁边加一小组"补丁矩阵"，只训练这组补丁。** 训练完，原模型 + 补丁 = 新模型。补丁文件通常只有几十 MB，而原模型几十 GB。
→ *这是个人开发者做微调唯一现实的方案。Ratchet 的训练后端优先支持 LoRA。*

**QLoRA**
LoRA 的加强版：先把原模型压缩成 4-bit（省 4 倍显存），再在上面做 LoRA。让单张消费级显卡（如 RTX 4090，24GB）也能微调 33B 模型。

**RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）**
ChatGPT 之所以"听话"，靠的就是这个。三步：
1. 让模型对同一问题生成多个回答；
2. 人类标注员排序，哪个更好；
3. 用这些排序训练一个**奖励模型**，再用它指导原模型训练。

**奖励模型（Reward Model, RM）**
一个专门打分的模型。输入"问题 + 回答"，输出一个分数，代表"这个回答有多好"。它是 RLHF 的核心部件，作用是把"人类的主观偏好"变成"机器能优化的数字"。
→ *Ratchet 需要一个轻量替代品，见下方"验证器"。*

**PPO（Proximal Policy Optimization，近端策略优化）**
最经典的强化学习算法之一，OpenAI 2017 年提出。特点是更新时限制步子不能迈太大（"近端"），防止模型一下子训崩。RLHF 传统上用它，但它需要同时加载 4 个模型（策略、参考、奖励、价值），极其吃显存。

**DPO（Direct Preference Optimization，直接偏好优化）**
2023 年斯坦福提出。**跳过奖励模型这一步**，直接用"好答案 vs 坏答案"的配对数据做优化。效果接近 PPO，但只需要 2 个模型，代码量小一个数量级，训练稳定得多。
→ *现在是开源社区的主流方案。Ratchet 的训练后端首选 DPO。*

**GRPO（Group Relative Policy Optimization，组相对策略优化）**
DeepSeek 提出，DeepSeek-R1 用它训练。**对同一个问题采样一组答案，用组内的平均分当基准，比平均好的就鼓励、比平均差的就抑制。** 这样就不需要额外的"价值网络"来估计基准，显存省一大块。特别适合有明确对错的场景（数学、代码）。
→ *Ratchet 训练后端的高级选项。*

**RLVR（RL with Verifiable Rewards，可验证奖励的强化学习）**
不用人类标注，也不用奖励模型，而是用**能自动判对错的东西**当奖励：数学题对答案、代码跑单元测试、格式符合正则。DeepSeek-R1 的推理能力主要靠这个练出来。
→ *这是 Ratchet 奖励体系最该借鉴的思路：**优先用客观可验证的信号，而不是让另一个 AI 主观打分**。*

**RLAIF / Constitutional AI**
用 AI 代替人类做偏好标注（RLAIF），或者先写一部"宪法"（一组原则），让 AI 按宪法自我批评和修订（Constitutional AI，Anthropic 提出）。
→ *Ratchet 的"反思器"就是这个思路的轻量实现。*

**蒸馏（Distillation）**
让大模型生成高质量数据，用这些数据训练小模型。小模型学到接近大模型的能力，但跑得更快更便宜。
→ *Ratchet 用它做"能力转移"：闭源强模型当数据生产者，开源模型当被训练对象。*

> ⚠️ **必须澄清的一个常见误解**：蒸馏**不能**让闭源模型自己变强。
> 你调用 GPT 生成一万条优质回答，然后这些数据无处可去——你没有它的权重，无法更新它。
> 蒸馏改变的是**数据的流向**，不是**权重的归属**。所以在 Ratchet 里，准确的表述是：
> - **闭源模型**：只能走路线 B（非参数化）。这是物理限制，不是工程难度问题。
> - **开源模型**：路线 B + 路线 A 都能走，而且路线 B 积累的经验数据，正是路线 A 最需要的训练集。
> - **蒸馏的位置**：它是 A 和 B 之间的桥梁——用闭源强模型产出的高质量轨迹，去训练本地开源模型。
>   这叫能力转移（capability transfer），受益者是那个开源模型。

**灾难性遗忘（Catastrophic Forgetting）**
神经网络学了新任务后，把旧任务忘了。微调最常见的翻车方式：为了学会你的写作风格，模型把数学能力搞坏了。
→ *这是路线 A 的主要风险，也是 Ratchet 默认走路线 B 的重要理由。*

### 3.3 非参数化自强化相关（路线 B 的词汇，Ratchet 的主战场）

**RAG（Retrieval-Augmented Generation，检索增强生成）**
最主流的做法：**在提问前，先从知识库里检索出相关材料，塞进提示词，再让模型回答。** 模型不用"记住"知识，只需要"会读"知识。
→ *Ratchet 的经验召回本质就是一个针对"个人经验"的 RAG。*

**情景记忆（Episodic Memory）**
认知科学借来的词，指"具体发生过的事"的记忆（何时、何事、结果如何），区别于"语义记忆"（抽象的知识规律）。
→ *Ratchet 的经验库存的是情景记忆；反思器负责把情景记忆蒸馏成语义记忆（规则）。*

**Reflexion（反思）**
2023 年的经典论文。核心思路极简：**任务失败后，让模型自己用语言写一段"我为什么失败了，下次应该怎么做"，把这段话存下来，下次重试时读一遍。** 结果在编程任务上把 GPT-4 的通过率显著提升。
→ *这是 Ratchet "反思器"模块的直接理论来源。关键点：经验是用**自然语言**存的，不是梯度，所以人能读能改。*

**Self-Refine（自我精炼）**
生成 → 让模型自己批评 → 根据批评重写 → 循环。不需要额外训练，纯靠多次调用。

**STaR（Self-Taught Reasoner，自我训练的推理器）**
2022 年论文，"模型自我强化"最早的可行范式：让模型自己生成推理过程，**只保留答对的那些**，用它们回头微调模型。答错的题，把正确答案给它看，让它反推一个能到正确答案的推理过程（叫"理性化 rationalization"），也拿来训练。
→ *这个"筛选成功轨迹 → 回灌训练"的循环，Ratchet 会在路线 A 后端完整实现。*

**技能库（Skill Library） / Voyager**
2023 年 NVIDIA 的 Voyager 项目，在 Minecraft 里做了一个终身学习 agent。三大件：
1. **自动课程**：自己给自己定下一个该学什么的目标；
2. **技能库**：每学会一个动作（比如"做一把石镐"），就把对应的代码存进库里，以后可以直接调用或组合；
3. **迭代提示**：把环境反馈和错误信息喂回去，让它改代码直到能跑。

结果：Voyager 获得的独特物品数是之前方法的 3.3 倍，而且**技能库可以整体迁移给一个新 agent，新 agent 直接继承全部能力**。
→ *这是"经验积累产生复利"最有说服力的证据。Ratchet 的经验条目设计成可复用、可组合的"技能"，灵感来自这里。*

**提示进化（Prompt Evolution）**
把提示词当成"基因"：维护多个提示变体，用实际表现打分，淘汰差的、保留好的、对好的做变异（改措辞、加约束、调结构）产生下一代。本质是**进化算法**用在文本上。
→ *Ratchet 的 `prompt_evolver` 模块。*

**多臂老虎机（Multi-Armed Bandit）**
想象一排老虎机，每台中奖率不同但你不知道。你只有有限次数，怎么在"多试试没玩过的机器（探索）"和"多玩已知最好的那台（利用）"之间平衡？这就是 bandit 问题。它是强化学习最简单的形式（没有状态转移）。
→ *Ratchet 面临一模一样的问题：手上有 5 个提示变体，每次交互只能选一个，怎么选才能长期收益最大？用 bandit 算法解决。这是 Ratchet "强化学习"成分最实打实的部分。*

**UCB（Upper Confidence Bound，置信上界）**
一种 bandit 策略：不只看某个选项的历史平均分，还看它"被试过的次数"。试得少的，给它一个"乐观加成"，逼系统去探索。公式思想：`选择 (平均分 + 不确定性加成) 最高的那个`。

**Thompson Sampling（汤普森采样）**
另一种 bandit 策略，效果更好也更优雅：给每个选项维护一个概率分布（"我觉得它的成功率大概在 0.6～0.8 之间"），每次决策前从每个分布里**随机抽一个数**，选抽到最大的那个。试得少的选项分布宽，抽到高数的机会就大，自然实现探索。
→ *Ratchet 默认用 Thompson Sampling。实现只要几十行代码，效果可靠。*

**LLM-as-a-Judge（大模型当裁判）**
让一个强模型去评价另一个模型的输出质量。便宜、可扩展，但有已知偏差：**位置偏差**（倾向于选排在前面的）、**长度偏差**（倾向于选更长的）、**自我偏好**（倾向于选和自己风格像的）。
→ *Ratchet 用它，但只作为**兜底奖励源**，且优先级低于客观验证。*

### 3.4 数据与检索

**Embedding（嵌入向量）**
把一段文本变成一串数字（比如 1536 个浮点数），使得**语义相近的文本，它们的数字串也相近**。这样"找相关内容"就变成了"找距离近的向量"，计算机算得飞快。
→ *Ratchet 用它实现"这次的任务和过去哪些经验相关"的语义匹配。*

**余弦相似度（Cosine Similarity）**
衡量两个向量方向有多接近的标准方法，结果在 -1 到 1 之间，越接近 1 越相似。

**向量数据库（Vector Database）**
专门存向量、并支持"给我找出最相似的 10 个"这种查询的数据库。当数据量大时，逐个比对太慢，需要专门的索引算法。常见的有 Chroma、Qdrant、Milvus、LanceDB、Pinecone。
→ *你之前问的三个选项里的"独立向量数据库"就是指这个。Ratchet MVP 阶段不引入，见下面 sqlite-vec。*

**HNSW（Hierarchical Navigable Small World）**
目前最主流的**近似最近邻**索引算法。它构建一个多层的图结构，查询时从顶层稀疏图快速跳跃到大致区域，再逐层细化。代价是结果"近似"而非绝对精确，换来的是千倍速度提升。

**sqlite-vec**
SQLite 的一个向量搜索扩展（作者 Alex Garcia）。**它让你在一个普通的 `.db` 文件里同时做关系查询和向量查询，不需要额外部署任何服务。**
→ *这是 Ratchet 的推荐选择。理由：单文件、零依赖服务、可 git 忽略可备份、对用户完全透明。*

**BM25**
经典的关键词检索打分算法（搜索引擎的老底子）。它擅长精确匹配术语，比如你搜 "LoRA" 它一定能找到含 "LoRA" 的文档，而向量检索有时会漏。

**混合检索（Hybrid Search）**
同时用 BM25（关键词）和向量（语义），再把两路结果融合排序。实践中几乎总是比单用一种好。
→ *Ratchet 的检索器采用混合方案。*

**SQLite**
一个"文件即数据库"的关系型数据库。整个数据库就是一个 `.db` 文件，不需要启动服务，Python 标准库自带支持。
→ *你之前问的三个选项里的"SQLite"就是这个。Ratchet 用它存所有结构化数据。*

### 3.5 工程与分发

**Agent（智能体）**
能自主规划、调用工具、执行多步任务的 AI 系统。不只是聊天，而是"给个目标，它自己想办法完成"。Cursor、Claude Code、千问工作助理都是 agent。
→ *Ratchet 要能接入这些 agent，让它们越用越强。*

**MCP（Model Context Protocol，模型上下文协议）**
Anthropic 在 2024 年底提出的开放协议，现在已被广泛采纳（包括 OpenAI、各大 IDE 和 agent 框架）。它规定了"agent 如何发现和调用外部工具/数据源"的标准接口。
**打个比方：MCP 之于 AI 工具，就像 USB-C 之于充电线。** 你实现一次 MCP 服务，所有支持 MCP 的客户端都能用。
→ *这是 Ratchet "接入各种 agent" 的最佳实现方式。写一个 MCP server，Cursor / Claude Desktop / 千问等都能挂载。*

**SDK / 库（Library）**
别人 `pip install` 之后，在自己代码里 `import` 来用的东西。

**CLI（Command Line Interface，命令行工具）**
在终端里敲命令用的程序，比如 `ratchet init`、`ratchet chat`。

**CI（Continuous Integration，持续集成）**
每次你推代码到 GitHub，服务器自动跑一遍测试和检查。GitHub Actions 是 GitHub 自带的免费 CI。
→ *开源项目的"质量信号"。有绿色 CI 徽章的项目，可信度高得多。*

**License（开源许可证）**
规定别人能怎么用你的代码。主流选择：
- **MIT**：最宽松，随便用，保留版权声明即可。**推荐 Ratchet 用这个**，最利于传播。
- **Apache 2.0**：类似 MIT，但额外有专利授权条款，企业更喜欢。
- **GPL 3.0**：传染性，别人用了必须也开源。会劝退商业用户。

**MVP（Minimum Viable Product，最小可行产品）**
能跑通核心价值闭环的最小版本。不是"功能少的残缺品"，而是"五脏俱全的小个子"。

## 4. Ratchet 的理论骨架：非参数化路线为什么也算强化学习

这一节很重要，因为它是这个项目在技术上的正当性论证。如果有人质疑"你不动权重，凭什么叫强化学习"，答案在这里。

强化学习的标准框架有五个要素：**状态（State）、动作（Action）、奖励（Reward）、策略（Policy）、策略更新（Policy Update）**。

Ratchet 严格对应：

| RL 要素 | Ratchet 中的实现 |
|---|---|
| **状态 State** | 当前任务描述 + 用户画像 + 已检索到的相关经验 + 对话上下文 |
| **动作 Action** | 选择哪一个提示变体 / 调用哪一套工具组合 / 用哪个推理策略（如"直接答" vs "先反思再答" vs "拆成子问题"） |
| **奖励 Reward** | 验证器打分（单元测试通过 / 规则匹配 / 用户显式点赞点踩 / LLM 裁判兜底） |
| **策略 Policy** | Thompson Sampling 维护的、每个动作的成功概率分布 |
| **策略更新** | 每次拿到奖励后更新 Beta 分布参数；周期性地把高分经验蒸馏进系统提示 |

**区别在于策略的表示形式**：传统 RL 的策略是神经网络的权重，Ratchet 的策略是「概率分布 + 可读文本规则的集合」。**更新机制的数学本质是一样的**——都是根据奖励信号，调整未来选择各动作的概率。

这有一个正式的名字：**上下文强化学习（In-Context RL）** 或 **语言化的策略优化**。近年学界已有相当多工作在这个方向（Reflexion、Voyager、以及一系列 "LLM as optimizer" 的论文），证明这条路是站得住脚的，不是我们自己造的概念。

### 四个自强化杠杆

Ratchet 靠四个动作形成闭环，缺一不可：

```
① 记忆（Memory）    把每次交互的输入、输出、结果、评分存下来
        ↓
② 反思（Reflection）把失败案例蒸馏成显式规则："遇到 X 类任务时，不要 Y，应该 Z"
        ↓
③ 择优（Selection）  在多个候选策略间，用 bandit 算法挑表现最好的
        ↓
④ 重写（Rewrite）    周期性地把高频有效规则压缩进系统提示，形成"新的默认人格"
        ↓
    （回到①，下一轮起点更高）
```

**复利效应**就来自这个循环：第 100 次交互时，模型能调取前 99 次积累的经验，起点远高于第 1 次。这与 Voyager 的技能库、以及人类的"经验积累"是同构的。

```

    │
```

```
    ├─► Retriever 混合检索，召回 Top-K 条相关经验与规则
    ├─► Policy（Thompson Sampling）从候选提示变体中选一个
    │
    ▼

    │
    ▼

    │
    ▼
输出结果
    │
    ├─► Verifier 打分（优先级：客观验证 > 用户反馈 > LLM 裁判）

    ├─► Policy 更新该变体的 Beta 分布参数
    │
    ▼

    ├─► Reflector：低分事件 → 反思 → 新规则入库
```

### 5.5 治理层：人类审计面板（Human Governance Panel）

这是整个项目**最重要的安全设计**，由用户提出。核心思路：既然经验库决定模型行为，那用户必须能随时看见它、并能删掉它。

#### 设计原则：非对称权限（Asymmetric Permissions）

不能让治理面板变成"第二个对话入口"——如果用户能在里面自由写文本，就等于绕过了正常交互路径直接给模型下指令，注入风险不可控。

所以权限这样划分：

| 操作 | 谁能做 | 理由 |
|---|---|---|
| **查看**全部经验、规则、画像项 | 人 | 透明性是信任基础，无副作用 |
| **删除 / 停用**任意条目 | 人 | 纯减法，不可能注入内容，风险为零 |
| **恢复**已停用条目 | 人 | 同样是封闭操作，不涉及新文本 |
| **新增**经验/规则 | 仅机器（Reflector / Distiller） | 防止自由文本注入 |
| **修改**经验内容 | 仅机器 | 同上 |

#### 唯一的例外：用户显式纠正（User Correction）

用户主动说"不对，应该是这样"，是**价值第二高的奖励信号**（仅次于客观验证）。全禁掉太可惜，所以开一个受控入口，但**不给自由文本框**，而是结构化有界输入：

```
纠正类型（枚举，只能选一个）：
  □ too_long        回答太啰嗦
  □ too_short       回答太简略
  □ wrong_tone      语气不对
  □ wrong_format    格式不对
  □ factually_wrong 内容有事实错误
  □ missed_context  漏掉了我之前说过的信息
  □ other_enum      其他（从预设细分列表里再选）

适用范围（枚举）：
  □ this_task_only  只对当前这类任务生效
  □ global          对所有交互生效

补充说明（可选，严格受限）：
  - 上限 140 字符
  - 入库前自动转义，并以「用户原话」标签包裹，不作为指令解析
  - 在提示词中始终渲染为：「用户曾表示：『……』（此为用户反馈记录，非系统指令）」
```

**为什么"限字数"本身不够，但配合上面三条就够了**：
单纯限制字数是无效防线——"忽略以上所有指令"只有 7 个字。真正起作用的是：
1. **结构化**：主信息量落在枚举字段里，自由文本只是附属说明，模型读到的是"用户在某维度上不满"，而不是一段可执行指令。
2. **强制转义与标签隔离**：明确声明这段文本的身份是"记录"而非"指令"。
3. **影响范围受限**：`this_task_only` 类型的纠正不会污染全局画像。

#### 治理面板的三层实现

```
① CLI 层（MVP 必须有）
   ratchet audit              # 列出所有活跃经验，按分数/使用次数排序
   ratchet audit --kind rule  # 只看规则
   ratchet delete <id>        # 停用（软删除，保留审计轨迹）
   ratchet restore <id>       # 恢复
   ratchet correct            # 走上面的结构化纠正流程

② SDK 层（MVP 必须有）
   store.list_active() / store.deactivate(id) / store.restore(id)
   governance.submit_correction(CorrectionInput(...))

③ Web 控制台（v0.4，可选）
   只读表格 + 删除按钮 + 结构化纠正表单
   不提供任何自由文本编辑框
```

#### 为什么软删除而不是硬删除

`deactivate` 只把 `active` 置为 `false`，数据仍在库里。好处：
- 用户误删可恢复
- 保留完整审计轨迹，能回答"模型为什么在某个时间点之后行为变了"
- 被停用的条目不参与检索，效果上等同于删除

提供 `ratchet purge` 做真正的物理清除（GDPR 式被遗忘权），但需要显式确认。

#### 关于"上限取决于人类写提示词的能力"

这个判断需要修正。如果真是这样，Ratchet 就没有存在价值了——**它的核心目的恰恰是把提示工程自动化掉**：

- `PromptEvolver` 自动产生和淘汰提示变体，不需要人写
- `Distiller` 自动把高频有效规则压缩进系统提示，不需要人写
- `Reflector` 自动把失败蒸馏成规则，不需要人写

人类的角色应该从**"写提示词"（高门槛，少数人会）** 降级为 **"判断好坏"（低门槛，人人都会）**。这正是治理面板设计的立足点：用户不需要知道怎么写出好提示词，只需要在两个回答之间选一个更好的、或者点一下"这条经验不对，删掉"。

**Ratchet 真正的上限由三个因素决定**：

| 上限因素 | 说明 | 缓解手段 |
|---|---|---|
| **奖励信号的质量** | 如果打分不准，系统会朝错误方向优化，越努力越糟 | 奖励源分级（客观验证 > 用户反馈 > LLM 裁判），裁判权重设上限 |
| **检索精度** | 经验库大了以后，召回不准就等于没有 | 混合检索 + 蒸馏压缩 + 低分自动下架 |
| **基座模型能力** | 模型本来不会的东西，Ratchet 教不会 | 路线 A 训练后端，真正提升基座 |

**这三者里，人类写提示词的能力一个都不占。** 人类提供的是"判断力"，而判断力比表达能力便宜得多。

## 7. 风险与边界：这个项目做不到什么

诚实地写下来，比夸大宣传更能赢得开源社区的信任。这部分**建议原样放进 README**。

### 7.1 技术风险

**① 经验污染（Experience Poisoning）**
一条错误的"经验"被存进去后，会在后续所有相关任务里被反复召回，把模型持续带偏。**这是本项目最大的实际风险。**

对策：
- 每条经验带 `score` 和 `uses`，被采用后如果导致低分，反向扣分；分数低于阈值自动 `active=false` 下架。
- 检索结果**永远标注来源和置信度**，让下游模型自己判断要不要信。
- 提供 `ratchet audit` 命令，一键列出所有活跃经验供人工审查。
- 硬上限：单个任务注入的经验条数不超过 K，总 token 不超过预算的 30%。

**② 奖励劫持（Reward Hacking）**
如果用 LLM 当裁判，系统可能学会"写得像好答案"而不是"真的是好答案"——比如堆砌术语、拉长篇幅来骗高分。

对策：
- 奖励源严格分优先级：**客观可验证 > 用户显式反馈 > LLM 裁判**。
- LLM 裁判的权重设上限（如不超过总奖励的 30%）。
- 裁判时同时提供"长度惩罚"和"位置随机化"以缓解已知偏差。
- 借鉴 RLVR 思路：能自动验证的场景（代码跑测试、数学对答案、格式校验）**一律优先用自动验证**。

**③ 画像误判的自我强化**
系统错误地认为"这个用户喜欢极简回答"，之后一直给极简回答，用户没纠正，置信度反而越来越高，错误被锁死。

对策：
- 置信度衰减：长时间没有新证据支撑的画像项，置信度自动下降。
- 周期性主动确认：高影响画像项定期在交互中轻量求证。
- `ratchet profile --reset` 一键清空。

**④ 隐私泄露**
经验库里会存下大量用户的真实工作内容、代码、个人信息。

对策：
- **默认全本地，零网络上传**（除了调用大模型 API 本身）。
- 入库前可选的脱敏管道（正则识别邮箱/手机号/密钥/token 并打码）。
- `.db` 文件默认加入 `.gitignore`，防止误提交。
- 明确的导出/删除命令，支持 GDPR 式的"被遗忘权"。

**⑤ 成本失控**
反思、进化、裁判都要额外调用大模型，token 成本可能是普通对话的数倍。

对策：
- 所有增强动作都可开关，且默认异步/批量执行。
- 实时成本统计（`event` 表里有 `cost` 字段），`ratchet status` 直接显示本月花费。
- 反思设触发阈值，不是每次失败都做。

### 7.2 能力边界（必须坦白的部分）

- **它不会让模型学会原本完全不会的东西。** 一个不会写 Rust 的模型，装了 Ratchet 还是不会写 Rust。它提升的是"调用已有能力的效率"和"避免重复犯错"。
- **它对基础能力弱的模型帮助有限。** 反思本身也需要模型有足够的理解力。
- **提升不是无限复利。** 经验库到一定规模后，检索精度下降、边际收益递减，需要靠蒸馏和淘汰来维持质量。
- **"任何大模型"指的是任何提供文本接口的模型**，不包括无法编程调用的封闭产品。
- **训练后端不保证提升。** 微调可能无效甚至有害，需要用户自己评测。

## 附：一句话总结这个项目

> **Ratchet 是一个本地优先的自强化引擎。它不改动大模型的权重，而是围绕模型建立一套"记忆—反思—择优—重写"的强化学习闭环：把每一次交互的结果变成可检索、可验证、可复用的经验，让同一个模型在你手里用得越久，表现越好。对开源模型，它还能把积累的经验导出为训练数据，真正更新权重。**
